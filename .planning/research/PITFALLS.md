# Pitfalls Research — Flutter Mobile Skeleton 2026

**Domain:** Flutter skeleton refresh (2026) — native rebase, Drift migration, sealed classes, flutter_bloc 9, auto_route 10, full Firebase wiring, flavors, RIVE, onboarding, coach marks, bootstrap rename, very_good_analysis.
**Researched:** 2026-04-16
**Overall confidence:** HIGH for version-specific breakages; MEDIUM for RIVE/coach-mark timing; HIGH for Firebase/flavor config (well-documented).

## Summary

This refresh has nine places where getting it wrong blocks the entire milestone and another eight where getting it wrong costs half a day each. The two sharpest edges are:

1. **Native rebase vs. ObjectBox leftover state.** `flutter create .` overwrites `MainActivity.kt`, `AppDelegate.swift`, `Podfile`, Gradle scripts, entitlements, and Info.plist. Anything the existing skeleton put there — including the ObjectBox native libs plumbing, `objectbox-model.json` in `lib/core/local_database/`, and the generated `objectbox.g.dart` — will either be erased silently or collide. Rebase **before** removing ObjectBox, not after.
2. **Firebase-flavor coupling.** Per-flavor `google-services.json` + per-flavor `GoogleService-Info.plist` + per-flavor `firebase_options_*.dart` + per-flavor OAuth client IDs + per-flavor App Check debug tokens form a tight network. A single mis-pathed file or one missing SHA-1 fingerprint breaks Google Sign-In silently at runtime with a generic `sign_in_failed` error.

Several of the rebase-era packages in `pubspec.yaml` also drift in ways that bite at build time rather than test time:

- `flutter_bloc` 9 makes `BlocListener` mount-aware (good) but dropped the `BlocOverrides` API (requires a refactor of any test that used it).
- `auto_route` 10 **deprecated `AutoRouteGuard` as a top-level class implementation** and forces moving global guards into a `guards` override on the router — the current `router.dart` will not compile after the bump without a structural change.
- `google_sign_in` 7.x requires `serverClientId` on Android (breaking change that surfaces as a runtime `GoogleSignInException` with no build-time warning).
- `very_good_analysis` will flood the existing `lib/` with ~30+ new analyzer errors on day one (`public_member_api_docs`, `sort_constructors_first`, `always_put_required_named_parameters_first`, strict-raw-types).

Below each pitfall is tagged with the roadmap phase that should own its prevention.

## Critical Pitfalls (can block the refresh)

### Native Rebase Gotchas

**What goes wrong:**
- `flutter create .` regenerates `android/app/build.gradle`, `android/app/src/main/AndroidManifest.xml`, `android/app/src/main/kotlin/.../MainActivity.kt`, `ios/Runner.xcodeproj/project.pbxproj`, `ios/Runner/AppDelegate.swift`, `ios/Runner/Info.plist`, and `ios/Podfile`. Any custom registrations (e.g., ObjectBox native entries, Flutter Secure Storage Android proguard rules, Google Sign-In URL scheme in `Info.plist`, Google Services plugin in `build.gradle`) are wiped without warning.
- The debug-keystore-for-release hack (`signingConfig = signingConfigs.debug` — [CONCERNS.md](.planning/codebase/CONCERNS.md) lines 19–23) is gone after regeneration, but **so is any `key.properties`-loading scaffolding** if you had added it.
- `android/settings.gradle` format changed between AGP 8.1 (pre-rebase) and 8.4+ (post-rebase): old skeleton uses legacy-style plugin declarations, new one uses pluginManagement blocks.
- Kotlin source folder stays at `com/example/skeleton/` even after regenerate if the old folder still exists; `flutter create` creates a new folder matching the current namespace but may not delete the old one.
- `ios/Podfile` platform pin goes from `13.0` → whatever current Flutter template emits (14.0 or 15.0 depending on Flutter version). Existing `Podfile.lock` must be deleted to avoid version conflicts.
- iOS entitlements file (`Runner.entitlements`) is NOT regenerated by `flutter create` — good for Apple Sign-In continuity, bad if you've never had one and expect it to appear.
- `android/app/src/main/res/values-night/` (dark mode colors) will be regenerated and **any custom splash XML is wiped**.

**Warning signs:**
- `Error: Namespace not specified. Specify a namespace in the module's build file.` — AGP 8+ requires `namespace` in `android/app/build.gradle`.
- `duplicate class com.google.android.gms.*` — Google Services plugin registered twice (old `apply plugin:` + new `plugins { id }` blocks both present).
- `Uncaught NSException: Could not find a valid GoogleService-Info.plist` — iOS bundle ID changed during rebase and Firebase console still has the old bundle.
- Silent app install with wrong app icon/label after rebase (Android manifest's `android:label` and `android:icon` reset to `@string/app_name` / `@mipmap/ic_launcher` defaults).
- Tests that import `package:skeleton/...` suddenly fail to resolve — `pubspec.yaml` name was changed in a rebase merge but not everywhere.

**Prevention:**
1. **Do the rebase on a separate worktree, not in place.** Run `flutter create` into a clean temp directory matching the same Flutter version, then three-way-diff against `android/` and `ios/` before copying over.
2. **Back up before rebase** (commit current state with a clearly tagged `pre-rebase` branch).
3. **Maintain a `rebase_manifest.md`** listing every native file with custom content: what the change is and why. Re-apply from the manifest after rebase.
4. **Do rebase first, Firebase wiring second.** Running `flutterfire configure` before rebase wastes work because the rebased project has a different bundle id / namespace.
5. **Delete `ios/Podfile.lock` and `ios/Pods/` before first post-rebase `pod install`.**
6. **Remove the old Kotlin source folder manually** (`android/app/src/main/kotlin/com/example/skeleton/`) after rename — `flutter create` does not clean stale folders.

**Phase:** Phase 1 (Native rebase) — this is the whole point of the phase.

### FlutterFire Version Drift

**What goes wrong:**
- `firebase_core` 3.10+ requires iOS deployment target 14 minimum; newer versions push to 15. The current `Podfile` pins 13.0, so first `pod install` after `firebase_core` update will fail with `The pod "Firebase/CoreOnly" required by the plugin "firebase_core" requires a higher minimum iOS deployment version than your application is targeting`.
- `firebase_crashlytics` 4.x dropped `recordFlutterError` (renamed to `recordFlutterFatalError`); the stub in current `startup_service.dart` already uses the new name, but any copy-pasted snippets from older tutorials will break.
- `firebase_app_check` 0.3.x changed provider initialization signature — `AppleProvider.debug` vs `AppleProvider.deviceCheck` vs `AppleProvider.appAttest` — and App Attest requires iOS 14+.
- `flutterfire_cli` generates `firebase_options.dart` in `lib/` by default. With flavors, you need `--out lib/firebase_options_dev.dart` and `--out lib/firebase_options_prod.dart` **and** separate `--android-out`/`--ios-out` for the platform config files. Forgetting any flag silently writes to the wrong path.
- `cloud_firestore` 5.x uses gRPC + BoringSSL pods (visible in current `Podfile.lock`) — bumps the iOS binary by ~8MB and requires `iOS 14+`.

**Warning signs:**
- `[firebase_core] CocoaPods could not find compatible versions for pod "firebase_core"` on `pod install`.
- `Error: The plugin "cloud_firestore" requires a higher minimum iOS deployment version than your application is targeting.`
- App Check activation silently fails on iOS with `DeviceCheckProvider` on simulator — DeviceCheck does not work in simulator, you must use `.debug` provider.
- `PlatformException(channel-error, Unable to establish connection on channel)` when calling any Firebase API before `Firebase.initializeApp`.

**Prevention:**
1. **Pin all Firebase packages together** to minor-compatible versions. Do not let resolver pick `firebase_crashlytics` 4.x alongside `firebase_core` 2.x.
2. **Align Podfile iOS platform to 15.0** (matching the AppFrameworkInfo.plist already at 12 needs correcting anyway per CONCERNS.md).
3. **Call `flutterfire configure` separately for dev and prod**, writing to flavor-specific paths.
4. **Never check `GoogleService-Info.plist` or `google-services.json` into version control if they contain secrets for prod** — add `android/app/src/prod/google-services.json` and `ios/config/prod/GoogleService-Info.plist` to `.gitignore` and document the setup flow in README.
5. **Source `firebase_options_*.dart` via conditional import** or flavor-specific main entry points, never via runtime `if` on `--dart-define`.

**Phase:** Phase 3 (Firebase wiring). Depends on Phase 2 (flavors).

### App Check Debug Configuration

**What goes wrong:**
- On Android, Play Integrity requires a signed release APK and published Play Console listing — **it cannot work locally**. You must use `AndroidProvider.debug` for dev builds and configure each developer's machine with a debug token registered in Firebase Console > App Check > Manage debug tokens.
- On iOS, `DeviceCheck` works on real devices from iOS 11+, but **fails silently in the iOS simulator**. `AppAttest` requires iOS 14+ and a real device. For simulator/debug, use `AppleProvider.debug`.
- Debug tokens are **device-specific and environment-specific**. A token printed on one developer's machine cannot be reused by another. Each developer must register their own.
- **Known regression (January 2025):** FlutterFire stopped printing the iOS debug token to the Xcode console in some versions. [firebase/flutterfire#16951](https://github.com/firebase/flutterfire/issues/16951) — you may need to enable `FIRDebugEnabled` via the Runner scheme arguments or tail device logs with `sudo log stream --predicate 'subsystem contains "AppCheck"'`.
- App Check **must be activated before any Firebase service call**. Putting `FirebaseAppCheck.instance.activate(...)` after `FirebaseFirestore.instance.collection(...)` silently enforces zero protection — Firestore uses an unattested token.

**Warning signs:**
- Firestore reads succeed in dev but fail in staging/prod with `permission-denied` (App Check is enforced in one env, not the other, and you shipped without enforcement to prod).
- iOS console shows no debug token at launch.
- `[FirebaseAppCheck][I-FAA...]` logs show `DeviceCheck failed: simulator not supported`.
- Play Integrity errors after switching flavors because each flavor's package name has its own App Check registration in Firebase console.

**Prevention:**
1. **Activate App Check immediately after `Firebase.initializeApp`**, before any DI registration that could trigger Firestore/Functions.
2. **Branch provider by `kDebugMode`**: `AppleProvider.debug` + `AndroidProvider.debug` in debug, real providers in release.
3. **Register a debug token per developer** in Firebase Console at project setup time. Document the flow in README with the `FIRDebugEnabled` argument trick for iOS.
4. **Test App Check enforcement separately** with a throwaway Firestore doc — flip enforcement in console between "Unenforced" and "Enforced" and verify the app still works with a valid debug token.
5. **Every flavor is a separate Firebase app** in the same project. Each needs its own App Check registration (Play Integrity SHA-256, DeviceCheck team ID, etc.).

**Phase:** Phase 3 (Firebase wiring) + Phase 6 (release keystore/signing, for Play Integrity SHA-256).

### Apple Sign-In Capability + Services ID

**What goes wrong:**
- `sign_in_with_apple` requires `com.apple.developer.applesignin` entitlement in `Runner.entitlements` **and** the App ID on developer.apple.com must have the "Sign In with Apple" capability checked. Forgetting either results in `AuthorizationErrorCode.unknown` at runtime on real devices (no build-time error).
- **Apple Sign-In requires iOS 13+ on real devices; does not work on iOS simulators below iOS 13.** With the skeleton targeting iOS 15, this is fine.
- For Android Apple Sign-In (via the package's web-based flow), you need an Apple Services ID (not the App ID) and a Return URL. The Services ID must be associated with a primary App ID and verified against the web domain.
- Apple requires any app that ships **any third-party federated sign-in** (Google, Facebook, etc.) to **also** offer Apple Sign-In on iOS, per App Store Review Guideline 4.8. The skeleton's decision to ship Google Sign-In makes Apple mandatory on iOS.
- Re-generating provisioning profiles after adding the capability is manual — Xcode's "Automatically manage signing" sometimes does not pick up the new entitlement until you toggle signing off and on.
- The first-time sign-in returns the user's email and full name **exactly once**; subsequent sign-ins return `null` for those fields. Forgetting to persist them on first sign-in means losing them forever.

**Warning signs:**
- `Provisioning profile "..." doesn't support the Sign in with Apple capability` at Xcode build.
- `AuthorizationError 1000 (unknown)` on real device sign-in attempt.
- User shows up in Firebase Auth with null email after first sign-in (Apple obscured the email via Private Relay; you must store it).
- On re-sign-in, you attempt to `updateProfile` with a null display name and overwrite the real one.

**Prevention:**
1. **Enable "Sign In with Apple" in the App ID BEFORE the first build.** Do this as part of Phase 2 (flavors + bundle IDs).
2. **Add the capability in Xcode via Signing & Capabilities, not by hand-editing `Runner.entitlements`** — the GUI triggers provisioning profile regeneration.
3. **On first Firebase sign-in, persist email + full name to Firestore/user document immediately.** Don't rely on re-fetching.
4. **Register a Services ID** for the Android/web flow during Phase 3 and link it to each flavor's App ID.
5. **Document that simulators won't work for Apple Sign-In** in the README troubleshooting section.

**Phase:** Phase 3 (Firebase wiring + Auth providers).

### Google Sign-In SHA per Flavor

**What goes wrong:**
- Firebase OAuth client IDs for Android require the **SHA-1** (and increasingly SHA-256 for App Check Play Integrity) fingerprint of the keystore that signs the APK. Each keystore produces a unique fingerprint.
- **Every keystore × every flavor × every Play Console signing key** is a separate fingerprint:
  - Debug keystore (machine-specific — each developer has a different one) → debug flavor → dev Firebase project
  - Release keystore → release flavor → prod Firebase project
  - Google Play App Signing key → published app → prod Firebase project (in addition to release)
- Missing any of these results in `sign_in_failed`/`PlatformException(sign_in_failed, 10:, null)` with error code `10` (DEVELOPER_ERROR) — a **generic** error with no hint that SHA-1 is the cause.
- **`google_sign_in` 7.x breaking change:** on Android, `serverClientId` is now required (or `clientId` is interpreted as serverClientId for backwards-compatibility). The serverClientId is the **Web Client ID** from the OAuth credentials — not the Android Client ID. [flutter/flutter#172073](https://github.com/flutter/flutter/issues/172073).
- On iOS, `serverClientId` = Web Client ID, `clientId` = iOS Client ID. Mixing these up causes `signInSilently` to return null without error.
- The `REVERSED_CLIENT_ID` URL scheme in `Info.plist` must match the iOS OAuth client, **per flavor**.

**Warning signs:**
- `PlatformException(sign_in_failed, com.google.android.gms.common.api.ApiException: 10:, null)` on Android.
- Silent null return on iOS from `GoogleSignIn().signIn()`.
- `GoogleSignInException: serverClientId must be provided on Android` after bumping to 7.x.
- Works on developer A's machine but not developer B's (different debug SHA-1s, only one is registered).
- Works in dev flavor but fails in prod flavor (flavor-specific OAuth clients not registered).

**Prevention:**
1. **Collect all SHA-1 fingerprints early**: debug keystore of every team member, release keystore, Play App Signing key. Document in `README.md > Google Sign-In Setup`.
2. **Register all of them in BOTH Firebase console AND Google Cloud Console OAuth credentials.** The console flow can diverge if you only update Firebase.
3. **Pass `serverClientId` explicitly** to `GoogleSignIn.initialize()` using the Web Client ID from `firebase_options_*.dart`.
4. **Automate SHA-1 collection** in the bootstrap script: `cd android && ./gradlew signingReport` and parse output; include it in the onboarding doc.
5. **Use `applicationIdSuffix` carefully**: if the dev flavor adds `.dev` to the applicationId, the Firebase Android app registration must use the suffixed package name.
6. **Re-register SHA-256 for Play Integrity / App Check** when adding App Check.

**Phase:** Phase 3 (Firebase wiring + Auth). Blocked by Phase 2 (flavors).

### ObjectBox → Drift Data Semantics

**What goes wrong:**
- **Reactive query semantics differ.** ObjectBox's `query().watch(triggerImmediately: true)` emits the full result set on every put/update. Drift's `.watchSingle()` / `.watch()` emits only on *changes to tables referenced by the query* — this is more efficient but can surprise code that expected an emission after any DB activity. For a single-row counter, both work, but pattern-copying into multi-table queries can under-emit if a table isn't joined.
- **Schema is relational, not entity-based.** Existing `CounterModel` uses `@Entity()` + `@Id()` — flat. Drift uses `Table` subclasses with `IntColumn`, `TextColumn`. Migrating requires thinking in tables + rows, not objects. For a skeleton example counter, this is trivial, but the pattern sets expectations for downstream apps.
- **`objectbox-model.json` leftover.** ObjectBox ships a model metadata file at `lib/core/local_database/objectbox-model.json` with entity UIDs locked. If not deleted, the JSON sits in the repo as dead weight, confusing new contributors.
- **`objectbox.g.dart` generated file.** Generated at `lib/core/local_database/objectbox.g.dart` per the `pubspec.yaml` `objectbox: output_dir: core/local_database` override. Not auto-deleted when the `objectbox_generator` dev dep is removed.
- **Drift code generation path.** By default, Drift generates `<database>.g.dart` next to the `@DriftDatabase` class. The skeleton's directory convention puts DB files under `lib/core/local_database/` — ensure the database file lives there and the `.g.dart` does too.
- **build_runner conflicts.** Running `flutter pub run build_runner build` with leftover ObjectBox annotations triggers "conflicting outputs" error. Must use `--delete-conflicting-outputs` **or** fully purge old generator outputs first.
- **SQLite initialization is different.** Drift needs `sqlite3_flutter_libs` (iOS/Android) or `sqlite3` (with a path provided). Forgetting this causes `SqliteException: no SQLite library found` at runtime, not build time.
- **NativeDatabase vs LazyDatabase.** Using `NativeDatabase.createInBackground()` (recommended for Flutter) runs SQLite on a separate isolate — emissions from `.watch()` cross an isolate boundary. For the skeleton, use `LazyDatabase(() async { ... path_provider ... NativeDatabase(...) ... })` pattern.
- **Schema migrations vs counter reset.** Drift requires `schemaVersion` and `MigrationStrategy`. The skeleton's counter won't need migrations initially but must scaffold them correctly or the next schema bump crashes.
- **Stream cancellation.** Same issue as ObjectBox — cubit's `StreamSubscription` must be cancelled in `close()`. Drift doesn't solve the existing bug documented in CONCERNS.md.

**Warning signs:**
- `SqliteException(14): unable to open database file`.
- `SqliteException(1): no such table: counters` at startup — migrations didn't run.
- `DatabaseException(code 14: unable to open database file)` on Android release builds — missing `sqlite3_flutter_libs` in `pubspec.yaml`.
- Build-time: "Tried to generate `counter.g.dart` which would overwrite existing file" — leftover ObjectBox generator config.
- Silent stream no-emit in reactive queries — watching a query that doesn't actually reference the mutated table.

**Prevention:**
1. **Remove ObjectBox fully before adding Drift.** Delete `lib/core/local_database/objectbox.g.dart`, `objectbox-model.json`, `objectbox` and `objectbox_flutter_libs` from `pubspec.yaml`, purge `@Entity()` imports. Run `flutter clean && flutter pub get`. Only then add Drift.
2. **Use `drift` + `drift_flutter` + `sqlite3_flutter_libs` + `drift_dev` (dev)**. Pin versions consistently.
3. **Scaffold `MigrationStrategy` with `onCreate` and `onUpgrade: stepByStep(...)` from day one.** Reference the official `database.steps.dart` generator (`dart run drift_dev make-migrations`).
4. **Use `NativeDatabase.createInBackground(file)` or `LazyDatabase`** in `open()` to keep SQLite off the UI isolate.
5. **Document the "one table → one watch" pattern** in the example feature so downstream apps don't mis-watch multi-table queries.
6. **Cancel stream subscriptions in `Cubit.close()`** — keep the fix from the existing bug on record.

**Phase:** Phase 4 (Drift migration). Must come after Phase 1 (native rebase) so SQLite native libs are not wiped.

### dartz → Sealed Class Exhaustiveness

**What goes wrong:**
- Existing `lib/features/home_page/presentation/cubit/home_cubit.dart` uses `.fold()` everywhere. Mechanical migration to `switch (result) { case Success(...) ... case Failure(...) ... }` works but misses the benefit of exhaustive analyzer checks if the sealed hierarchy isn't properly sealed.
- **Sealed classes must live in the same library to unlock exhaustiveness.** Scattering `SuccessResult`, `FailureResult` across files without the `sealed` modifier or spreading into different `part` files breaks the compiler check.
- **`Right(null)` smell (CONCERNS.md bug).** Current code returns `Right(null)` for `Either<Failure, void>`. In sealed-class land, this is fixed by modeling it as a `Result<void>` or `Result<()>` (unit-style) — but copy-paste migration will reproduce the smell.
- **Freezed vs plain sealed classes.** Tempting to reach for Freezed when sealed classes ship natively. With Dart 3 + pattern matching + sealed classes, Freezed is unnecessary for sum types — adding it is extra codegen + extra dep.
- **Existing `Failure` hierarchy** (`Failure.localDataNotFound`, `Failure.localDataSource`) uses factory constructors on a non-sealed parent. Moving this to `sealed class Failure` with subclasses is a breaking API change for any downstream caller that expected the factory pattern.
- **Pattern matching interaction with null safety.** `switch (result) { case Success(value: final v) => ... }` where `v` is nullable — destructuring preserves nullability. Forgetting this leads to null-in-non-null assignment.
- **Switch statements vs switch expressions.** Old `if (result.isLeft) ... else ...` maps cleanly to `switch (result)` statements. But the far better pattern is `final output = switch (result) { Success(:final value) => value, Failure(:final msg) => defaultFor(msg) };` — the expression form, which makes exhaustiveness enforcement critical.

**Warning signs:**
- `The type 'Result' is not exhaustively matched by the switch cases.` — your sealed hierarchy isn't actually sealed, or a subclass lives in a different library.
- Nulls leaking in `Success(value: final v)` destructure.
- Analyzer warnings about "dead code" in fall-through default cases — you added a default branch that's unreachable because the sealed class covers everything.
- `StateError: no element` in tests because migration left `.fold((l) => ..., (r) => ...)` calls on a type that no longer has `.fold`.

**Prevention:**
1. **Define `sealed class Result<T>` with `Success<T>` and `Failure<T>` subclasses in a single `lib/core/errors/result.dart` file.** Export via `part 'failure.dart';` if splitting.
2. **Write switch *expressions* not statements.** Force exhaustiveness at compile time.
3. **Model void returns as `Result<void>` or `Unit`-style**: `final class Unit { const Unit._(); static const Unit unit = Unit._(); }`.
4. **Migrate one call site at a time**, keeping `dartz` as a transitive dep until the last `.fold()` is gone, then remove `dartz` and run analyze.
5. **Re-run `flutter analyze` after each migration chunk** to catch missed call sites.
6. **Write migration codemod as a one-off dart script** or use `grep -rn "dartz" lib/` to locate every call.

**Phase:** Phase 5 (sealed classes + error handling).

### Flavors Misconfiguration (Firebase per-flavor)

**What goes wrong:**
- On Android, `google-services.json` location must match the flavor: `android/app/src/<flavor>/google-services.json`. If only `android/app/google-services.json` exists, both flavors use the same project — silent cross-contamination of events, users, crashes.
- `applicationId` + `applicationIdSuffix` interaction: if dev flavor uses `applicationIdSuffix ".dev"`, the full package name is `com.example.app.dev`. Firebase Android app must be registered with `com.example.app.dev`, not `com.example.app`. The FlutterFire CLI `--android-package-name` must be the final suffixed name.
- On iOS, **schemes vs configurations are different concepts**. Flutter flavors require **build configurations named `Debug-<flavor>`, `Release-<flavor>`, `Profile-<flavor>`** (literal `-` separator). Plain `Debug-dev` works, `Debug_dev` or `DebugDev` don't.
- iOS `GoogleService-Info.plist` must be copied per-flavor via a Run Script Build Phase. Committing the script incorrectly results in "Multiple commands produce" errors at build.
- Run Script Phase order matters: the copy must happen **before** the "Compile Sources" or at least before "Process Info.plist" depending on how Firebase reads the file.
- Xcode schemes are stored in `xcshareddata/xcschemes/` — **must be committed** (not auto-generated). Missing scheme = `flutter run --flavor dev` fails with `Xcode build failed`.
- `applicationIdSuffix` can conflict with the Firebase namespace in `google-services.json`: the Firebase SDK reads `package_name` from the manifest, but the Google Services gradle plugin generates `applicationId`-based code. Mismatch = `No matching client found for package name '...'`.

**Warning signs:**
- `No matching client found for package name 'com.example.skeleton.dev'` at runtime.
- `Multiple commands produce '.../GoogleService-Info.plist'` at Xcode build.
- `Xcode build failed. No such scheme 'dev'.` at `flutter run --flavor dev`.
- Events from dev flavor appearing in prod Analytics dashboard.
- Crashlytics symbols uploaded with wrong bundle ID.

**Prevention:**
1. **Name flavors `dev` and `prod` consistently across Dart, Android product flavors, iOS schemes, and Firebase project names.**
2. **Use FlutterFire CLI with explicit flags per flavor:**
   ```bash
   flutterfire configure \
     --project=my-app-dev \
     --out=lib/firebase_options_dev.dart \
     --ios-bundle-id=com.example.app.dev \
     --ios-out=ios/config/dev/GoogleService-Info.plist \
     --android-package-name=com.example.app.dev \
     --android-out=android/app/src/dev/google-services.json
   ```
3. **Use separate main entry points** (`lib/main_dev.dart`, `lib/main_prod.dart`) that import the right `firebase_options_*.dart` statically — avoids runtime branching on flavor.
4. **Test both flavors install side-by-side on one device** (different applicationIds must be achievable).
5. **Commit `.xcscheme` files** in `ios/Runner.xcodeproj/xcshareddata/xcschemes/`.
6. **Add a sanity check** in the bootstrap script that greps for `com.example.skeleton` after rename — a leftover reference is a silent bug.

**Phase:** Phase 2 (flavors). Must precede Phase 3 (Firebase wiring).

### Release Keystore

**What goes wrong:**
- Current `android/app/build.gradle` uses `signingConfigs.debug` for release with a `// TODO` ([CONCERNS.md](.planning/codebase/CONCERNS.md)). This ships debug-signed APKs to Play Store — **rejected at upload**.
- Debug-signed release builds **cannot coexist** on-device with prod release builds — package manager refuses the install because the signing cert differs.
- If the skeleton ships **with a real keystore committed**, every downstream app is signed by the same key — catastrophic for app ownership (Google Play App Signing assumes uniqueness).
- Skipping `key.properties` on `.gitignore` leaks the storePassword into git history.
- Forgetting to back up the keystore = unrecoverable loss of app ownership on Play Store if not using Play App Signing.

**Warning signs:**
- Play Console: `You uploaded an APK or Android App Bundle that was signed in debug mode`.
- `INSTALL_FAILED_UPDATE_INCOMPATIBLE: Package ... signatures do not match previously installed version`.
- Gradle error: `Keystore file not set for signing config release`.
- `key.properties` visible in `git log -- android/key.properties`.

**Prevention:**
1. **Ship a `key.properties.template` file**, not a real `key.properties`.
2. **Add `android/key.properties` and `android/app/*.jks` to `.gitignore`.**
3. **Read keystore from env/CI secrets** in a second iteration (document `CM_KEYSTORE_PATH` pattern if using Codemagic later).
4. **Document in README**: "Before shipping to Play Store, generate a release keystore with `keytool`, populate `key.properties`, and register the SHA-1/SHA-256 in Firebase console + Google Cloud OAuth."
5. **Add a sanity guard** in `build.gradle`: if `key.properties` exists, use it; else fall back to debug *with a loud comment* explaining this is not production-ready.
6. **Do NOT ship a keystore in the skeleton** under any circumstance.

**Phase:** Phase 2 (flavors + signing) or Phase 6 (release hardening). Documentation is enough for the skeleton; per-project setup is the downstream concern.

## Medium Pitfalls (fixable but time-consuming)

### flutter_bloc 8 → 9 API changes

**What goes wrong:**
- `BlocOverrides.runZoned(() => ..., blocObserver: ..., eventTransformer: ...)` is **removed**. Use `Bloc.observer = ...` and `Bloc.transformer = ...` globally.
- `BlocListener` now checks `mounted` before firing — behavior change. Any code that relied on firing after unmount breaks silently (typically for the better).
- `EmittableStateStreamableSource` is the new core interface; tests that extended `Bloc` via fakes need updating.
- `bloc_test` 10.0 is paired with bloc 9 — do not mix 9.x `flutter_bloc` with 8.x `bloc_test` (resolver will fail with "version solving failed").
- `emit.isDone` is now accurately tracked; `emit` after close is now a thrown error rather than silent no-op in some paths.

**Warning signs:**
- `BlocOverrides is undefined` after upgrade.
- `bloc_test` version solver error.
- Tests that awaited a state after `close()` now throw `StateError`.

**Prevention:**
1. **Bump `flutter_bloc: ^9.0.0` and `bloc_test: ^10.0.0` simultaneously.**
2. **Replace all `BlocOverrides.runZoned(...)` calls** with direct `Bloc.observer = MyObserver();` in `main()`.
3. **Run tests first**, fix test breaks, then run app.
4. **Keep the existing cubit pattern** — no structural change needed beyond the BlocOverrides removal.

**Phase:** Phase 5 (package upgrades).

### auto_route 9 → 10 codegen

**What goes wrong:**
- `AutoRouteGuard` is no longer a class you `implements`; global guards are defined by overriding the `guards` property on the router class.
- `pushNamed` → `pushPath`, `replaceNamed` → `replacePath`, `navigateNamed` → `navigatePath`, `popForced` → `pop`, `pathParams` → `params`. Old calls compile-error with "method not found".
- `router.pop` was renamed to `router.maybePop`. Old `pop()` behavior became `maybePop()`; new `pop()` is stricter.
- Deep link handling changed: hostless deep links (`scheme://page/sub-page`) are no longer auto-handled; must implement `deepLinkTransformer`.
- `NavigationResolver` now exposes a `.context` for guarded route context access and an `overrideNext` method for dynamic redirection.
- The generated `router.gr.dart` format changed — re-running `build_runner build --delete-conflicting-outputs` is mandatory.
- `router.dart` in the current skeleton uses `@AutoRouterConfig` annotation and extends `$AppRouter`. V10 no longer generates a `$AppRouter` class — you extend `RootStackRouter` directly.

**Warning signs:**
- `The class '$AppRouter' is not defined.` post-codegen.
- `The method 'pushNamed' isn't defined for the type 'AppRouter'.`
- Guards silently not firing after bump — they didn't get moved to the router's `guards` override.
- Deep links stop working.

**Prevention:**
1. **Read the [auto_route 10 changelog](https://pub.dev/packages/auto_route/changelog) before bumping.**
2. **Regenerate the router after bumping** with `--delete-conflicting-outputs`.
3. **Move onboarding guard** (`hasSeenOnboarding` check) into the `guards` list on `AppRouter` per v10 pattern.
4. **Search-and-replace deprecated method names** across `lib/`.
5. **Test navigation with `maybePop` vs `pop` semantics** — rare edge cases in tab navigators.

**Phase:** Phase 5 (package upgrades). Interacts with Phase 3 (onboarding guard depends on auto_route).

### RIVE splash flicker

**What goes wrong:**
- Native splash (via `flutter_native_splash`) paints until Flutter's first frame — then the Flutter-level RIVE splash screen paints. **Two splash transitions = flicker.**
- RIVE state machine has to be `init`ed **synchronously on first frame**; otherwise the Flutter splash shows a static first frame while the artboard loads.
- `.riv` asset preloading: if the `.riv` file isn't in `pubspec.yaml` assets or hasn't been precached via `RiveFile.asset` before the splash widget builds, the splash shows a blank for one frame.
- Animations that loop forever prevent the "splash done" callback from firing unless you use `onExit` on a one-shot state.
- `flutter_native_splash`'s `preserve()` / `remove()` pattern: if you call `preserve()` before `runApp` but never call `remove()`, the native splash sits forever behind the Flutter splash, wasting memory.

**Warning signs:**
- One-frame white/black flash between native and Flutter splash.
- RIVE splash shows a blank canvas for ~100ms.
- RIVE animation starts mid-way instead of from frame 0.
- Splash never dismisses.

**Prevention:**
1. **Match the background color** of `flutter_native_splash` to the RIVE canvas background — even if flicker happens, it's invisible.
2. **Precache the `.riv` file** with `RiveFile.asset(...)` in a `FutureBuilder` or in `main()` before `runApp`.
3. **Use `FlutterNativeSplash.preserve(widgetsBinding: ...)` before `runApp`** and `FlutterNativeSplash.remove()` on the RIVE state machine's exit callback.
4. **Keep the RIVE splash under 2 seconds** and provide a skip on tap for debug builds.
5. **Listen to the state machine's `onStateChange`** to trigger `remove()` precisely when the splash animation enters its exit state.

**Phase:** Phase 3 or 4 (RIVE integration).

### tutorial_coach_mark GlobalKey timing

**What goes wrong:**
- Targets are located by `GlobalKey.currentContext.findRenderObject()` — if the widget isn't laid out yet, `renderObject` is null and the package throws `It was not possible to obtain target position.`, which covers the app in a blocking white overlay forcing restart.
- Calling `showTour()` in `initState` runs before the widget tree's first layout pass → target not found.
- Hot reload preserves cubit state but GlobalKeys bind to old render objects → `currentContext` is stale.
- Navigating between screens during a tour breaks the next target (keys on the new screen haven't mounted).
- Calling `register(key, 'description')` on a key that's also used for semantic identifier (`Key('counter-fab')`) silently doesn't work — `GlobalKey` is needed specifically.

**Warning signs:**
- `TutorialCoachMark (ERROR): It was not possible to obtain target position.`
- White full-screen overlay after starting tour.
- First target highlight appears correctly, subsequent targets are mis-positioned.
- Hot reload during a tour → stale position.

**Prevention:**
1. **Defer `showTour()` with `WidgetsBinding.instance.addPostFrameCallback((_) => service.showTour())`.** Don't use `Future.delayed(Duration.zero, ...)` — it's racy.
2. **Handle null targets in `CoachMarkService.register`** — silently skip if the key's `currentContext` is null.
3. **Store GlobalKeys as static fields on the service**, not per-widget state.
4. **Abort and restart the tour** on navigation; don't try to persist across routes.
5. **Test the coach mark flow on slow simulators** — the race condition is less visible on fast machines.

**Phase:** Phase 4 or 5 (onboarding + tutorial integration).

### Bootstrap script false-positive replaces

**What goes wrong:**
- Naive `sed -i '' 's/com.example.skeleton/com.foo.app/g'` on the whole repo replaces `com.example.skeleton` inside `node_modules/`, `.gradle/`, `.dart_tool/`, `build/`, `Pods/`, etc. — polluting caches and causing build failures.
- Binary Info.plist files (rare in Flutter projects, but possible after Xcode optimization) store `CFBundleIdentifier` in binary format — string replacement corrupts them.
- `pubspec.yaml` package name change requires updating `import 'package:skeleton/...'` across every Dart file; missing one breaks imports silently as relative imports still work.
- iOS bundle id in `project.pbxproj` appears in multiple `buildConfiguration` blocks (Debug, Release, Profile × Runner, RunnerTests, RunnerDev, RunnerProd) — replacing only one leaves schemes inconsistent.
- Android namespace (`android.namespace` in build.gradle) and `applicationId` are separate but related — bootstrap must update both.
- Kotlin source folder path matches old package (`com/example/skeleton/`) — script must **move** files, not just rename references.
- Case-sensitive filesystems (Linux CI) vs case-insensitive (macOS dev) — renaming `Skeleton` → `MyApp` may silently fail on macOS if old path and new path differ only in case.

**Warning signs:**
- `Cannot find module 'skeleton'` in Android Studio after rename.
- `No matching file found for package:skeleton/main.dart`.
- iOS schemes break with "Missing target".
- Kotlin file still at old package path but references new package.
- CI fails while local dev works (case sensitivity).

**Prevention:**
1. **Whitelist paths** the bootstrap script touches: `lib/`, `android/app/`, `ios/Runner*/`, `pubspec.yaml`, `l10n.yaml`, `test/`, `README.md`. Exclude `build/`, `.dart_tool/`, `.gradle/`, `Pods/`, `ios/Runner.xcworkspace/`, `ios/Podfile.lock`.
2. **Write the script in Dart** (`tool/bootstrap.dart`), not bash — better error handling, platform-independent.
3. **Move Kotlin source folder** with `Directory.rename`, don't just edit path strings.
4. **Run `flutter clean` at the end** of the bootstrap script.
5. **Write a dry-run mode** that shows every file that would be changed before applying.
6. **Test the script itself** in `test/tool/bootstrap_test.dart` with a fixture directory.
7. **Fail loudly if `com.example.skeleton` still appears** after bootstrap — grep before the final `flutter pub get`.
8. **Never run string replacement on `.plist` binary files** — detect with `file --mime-type` and convert to XML with `plutil -convert xml1` first if needed.

**Phase:** Phase 6 (bootstrap script + DX).

### very_good_analysis retrofit cascade

**What goes wrong:**
- Switching from `flutter_lints` to `very_good_analysis` adds ~60 new rules (strict-inference, strict-raw-types, `public_member_api_docs`, `sort_constructors_first`, `always_put_required_named_parameters_first`, `cascade_invocations`, etc.).
- Requiring `errors-not-warnings` (author's stated intent) escalates all warnings to errors — **`flutter analyze` returns non-zero immediately** on first run.
- `public_member_api_docs` alone generates one error per undocumented public member — for a skeleton with ~20 classes, this is ~100+ errors.
- Generated files (`*.g.dart`, `*.freezed.dart`, `objectbox.g.dart`) will get flagged unless excluded via `analyzer: exclude:`.
- `sort_constructors_first` requires constructors before fields — rewriting every widget's constructor order.
- Lint settings cascade into `test/` — enforcing `public_member_api_docs` on test files is overkill.
- Adding `// ignore:` comments doesn't reset the lint on the next line, and adding too many pollutes the codebase.

**Warning signs:**
- `flutter analyze` returns 100+ errors on first run after lint swap.
- CI pipeline fails on `flutter analyze --fatal-infos`.
- Generated file errors block build (e.g., `injection.config.dart`).

**Prevention:**
1. **Adopt `very_good_analysis` BEFORE adding new code** — on existing `lib/`, do a one-time cleanup pass.
2. **Disable noisy rules in `analysis_options.yaml`** upfront: `public_member_api_docs: false` is almost universally disabled outside Very Good Ventures themselves.
3. **Exclude generated files:**
   ```yaml
   analyzer:
     exclude:
       - '**/*.g.dart'
       - '**/*.freezed.dart'
       - 'lib/core/router/router.gr.dart'
       - 'lib/core/injectable/injection.config.dart'
   ```
4. **Keep `errors-not-warnings` scoped to CI only**; local dev can have warnings.
5. **Document the lint strategy in README**: what's on, what's off, why.
6. **Address lints in one PR** to avoid conflating linting noise with actual refactors.

**Phase:** Phase 5 or 6 (lint modernization).

### ObjectBox leftover files

**What goes wrong:**
- `lib/core/local_database/objectbox.g.dart` is generated; `lib/core/local_database/objectbox-model.json` is committed metadata. Removing `objectbox` from `pubspec.yaml` doesn't delete these.
- `objectbox_flutter_libs: any` (loose constraint per CONCERNS.md) leaves transitive native pod entries in `ios/Podfile.lock` — `pod deintegrate` needed.
- `.flutter-plugins-dependencies` lists `objectbox_flutter_libs` across 5 platforms; will be regenerated on next `flutter pub get` but may have stale cached entries.
- `@Entity()` annotations in `counter_model.dart` — removing them requires the model to become a plain data class (or a Drift `Table` subclass).
- The `objectbox: output_dir: core/local_database` override in `pubspec.yaml` — leftover, but harmless.
- iOS Pods directory still references `ObjectBox` frameworks.

**Warning signs:**
- `pod install` warns about orphaned `ObjectBox` pod.
- `Counter` entity annotations won't compile after removing the dep but not the import.
- `objectbox.g.dart` file exists but its imports resolve to nothing.

**Prevention:**
1. **Remove in this order**: (1) delete `lib/core/local_database/objectbox*` files, (2) remove `@Entity`/`@Id` imports from `counter_model.dart`, (3) remove `objectbox`, `objectbox_flutter_libs`, `objectbox_generator` from `pubspec.yaml`, (4) `flutter clean`, (5) delete `ios/Pods/` and `ios/Podfile.lock`, (6) `flutter pub get` + `pod install`.
2. **Remove the `objectbox:` block from `pubspec.yaml`.**
3. **Verify `.flutter-plugins-dependencies` no longer lists objectbox** after `flutter pub get`.
4. **Delete the stale Kotlin/Swift entries** (none for ObjectBox, but same principle).

**Phase:** Phase 4 (Drift migration, step 1).

### Removed platforms leftover refs

**What goes wrong:**
- `.flutter-plugins-dependencies` enumerates plugin support for iOS/Android/macOS/Linux/Windows/web (per INTEGRATIONS.md). Deleting `web/`, `macos/`, `linux/`, `windows/` directories alone doesn't remove transitive plugin registrations.
- `cloud_firestore_web`, `firebase_core_web`, etc. are separate packages that Flutter's resolver pulls when any platform in the project manifest includes web. Removing `web/` directory disables web builds but doesn't trim the web-specific transitive packages.
- `pubspec.yaml` doesn't explicitly declare platforms (this is only in `flutter create` defaults) — removal must be directory-based.
- iOS podfile resolves macOS-friendly variants of plugins if `macos/` exists; removing it cleans up the pod graph.
- Xcode project schemes may reference the macOS target — if not cleaned up, `flutter run -d macos` still tries.

**Warning signs:**
- `flutter pub get` still pulls `firebase_core_web`, `cloud_firestore_web` after removing `web/`.
- `flutter devices` lists macOS/Windows/Linux as targets after deletion.
- Xcode workspace shows stale macOS target.

**Prevention:**
1. **Delete platform directories AND run `flutter clean`** afterwards.
2. **Run `flutter pub get`** — resolver will drop transitive web packages if web is not in the project.
3. **Check `flutter devices`** after cleanup — if macOS/Windows/Linux still appear, verify `flutter config --no-enable-*`.
4. **Delete from VCS history** if sensitive config was ever in macOS/Windows directories.
5. **Document in README** that this is a mobile-only skeleton; re-add platforms per-project with `flutter create --platforms=web .` if needed.

**Phase:** Phase 1 (native rebase).

### PL template ARB decision

**What goes wrong:**
- Current `l10n.yaml` sets `template-arb-file: app_pl.arb`. This is Flutter's "source of truth" locale.
- Per CONCERNS.md bugs, `app_en.arb` is already drifting — missing `homePage_decrementButton` and `homePage_error`. The template is authoritative for key presence, so the English version throws at runtime.
- Most i18n tooling assumes English-as-source: Crowdin, Lokalise, Phrase, Weblate all default to English source. A Polish-source project needs manual config.
- `flutter gen-l10n --untranslated-messages-file` compares against the template — if the template is Polish, it flags missing English, which is backward for most contributors.
- Comments and docstrings in `.arb` files target the *source* language — author writes `@homePage_title: {"description": "..."}` in Polish, translator writes English from that.
- Accessibility/UX copy decisions (button labels, error messages) are inherently easier to make English-first since most UX patterns are documented in English.

**Warning signs:**
- English users hit `null` localization calls → red screen.
- Contributors writing keys in English forget to add PL translation → template is stale.
- i18n tools reject the config or misinterpret source.
- `untranslated-messages-file` output confuses the team.

**Prevention (strongly recommended: switch to English-as-source):**
1. **Switch `template-arb-file: app_en.arb`** in `l10n.yaml`.
2. **Add `@@x-source-locale: "en"`** at the top of `app_en.arb`.
3. **Ensure `app_en.arb` has every key from `app_pl.arb`** (fix CONCERNS.md drift).
4. **Add a CI check**: `flutter gen-l10n --untranslated-messages-file=untranslated.json && test ! -s untranslated.json`.
5. **Document the source-language convention** in README so future translators understand the workflow.

**Decision for roadmap:** Switch to English-source as part of the refresh. Polish is not lost — PL translations continue in `app_pl.arb`.

**Phase:** Phase 6 (docs + i18n cleanup) or bundled with Phase 3 (onboarding copy).

## Minor Pitfalls

### intl codegen after locale changes

**What goes wrong:**
- `flutter gen-l10n` needs a rerun after every `.arb` edit. Forgetting means `AppLocalizations.of(context)!.homePage_title` still returns the old string.
- `pubspec.yaml` must have `generate: true` under `flutter:` — already set.
- `intl: ^0.19.0` is pinned below Flutter's current floor; bump to `^0.20.0` with the SDK update.
- ICU message format edge cases: plurals with `{count, plural, =0{...} =1{...} other{...}}` — easy to typo.

**Prevention:**
1. **Re-run `flutter gen-l10n` after each ARB edit** (or let `flutter run` regenerate automatically).
2. **Bump `intl: ^0.20.0`** alongside SDK upgrade.
3. **Add a pre-commit grep** for `AppLocalizations.of(context)!` calls that don't have corresponding keys in both ARB files.

**Phase:** Phase 6 (cleanup).

### Multi-dex

**What goes wrong:**
- With `minSdkVersion` < 21, Android 64K method limit is reachable with full Firebase + Google Sign-In + Apple Sign-In + Drift + RIVE.
- Flutter's current default `minSdk` is 21 (per latest `flutter create`), so this is **likely a non-issue** after the native rebase.
- If a consuming project lowers `minSdk` below 21, multi-dex must be explicitly enabled.

**Warning signs:**
- `The number of method references in a .dex file cannot exceed 64K.`
- `java.lang.NoClassDefFoundError: Failed resolution of: ...`  at runtime on Android < 21.

**Prevention:**
1. **Keep `minSdkVersion >= 21`** per Flutter default.
2. **If a downstream project needs lower `minSdk`**, document how to enable multi-dex:
   ```gradle
   defaultConfig {
       multiDexEnabled true
   }
   dependencies {
       implementation 'androidx.multidex:multidex:2.0.1'
   }
   ```
3. **Not a skeleton concern** unless downstream is Android 4.x.

**Phase:** Phase 1 (native rebase) — verify `minSdkVersion >= 21` is the default.
