# Native Rebase Runbook

When to use: Rebasing the skeleton onto a new Flutter major release (e.g., 3.41.5 -> next).

Last performed: 2026-04-16 (Flutter 3.41.5)

## Prerequisites
- FVM installed
- Xcode + CocoaPods
- Android Studio + Android SDK
- Clean working tree (commit or stash all changes)

## Pre-Rebase Safety
Step 0: Commit current state on a named branch as recovery point.
```bash
git checkout -b rebase-flutter-X.Y.Z
git add -A && git commit -m "pre-rebase snapshot"
```

## Procedure

### Step 1: Bump FVM Pin
- Update `.fvmrc` to the new Flutter version
- Run `fvm install X.Y.Z && fvm use X.Y.Z`
- Verify: `fvm flutter --version` reports the new version
- What can go wrong: FVM may need updating first (`dart pub global activate fvm`)

### Step 2: Generate Fresh Scaffold
- Create a temp directory and generate fresh Flutter scaffolding:
```bash
mkdir /tmp/flutter-rebase-scaffold
cd /tmp/flutter-rebase-scaffold
fvm flutter create --platforms=android,ios --org com.example skeleton_temp
```
- Verify: temp dir contains android/ and ios/ with the new SDK's defaults
- What can go wrong: `flutter create` flags may change between majors — check `flutter create --help`

### Step 3: Delete Old Native Directories
- From the skeleton project root:
```bash
rm -rf android/ ios/
```
- Also delete non-mobile platforms if they were re-created:
```bash
rm -rf web/ macos/ linux/ windows/
```
- Run `flutter clean` to clear cached references

### Step 4: Copy Fresh Scaffold
```bash
cp -R /tmp/flutter-rebase-scaffold/skeleton_temp/android ./android
cp -R /tmp/flutter-rebase-scaffold/skeleton_temp/ios ./ios
```
- Verify: `ls android/app/build.gradle.kts` (or .gradle depending on SDK version) exists
- What can go wrong: Flutter may switch between Groovy (.gradle) and Kotlin DSL (.gradle.kts) — the 3.41.5 rebase moved to Kotlin DSL

### Step 5: Update iOS Podfile Floor
- Open `ios/Podfile` and set the platform floor:
```ruby
platform :ios, '15.0'
```
- Update `IPHONEOS_DEPLOYMENT_TARGET` in `ios/Runner.xcodeproj/project.pbxproj` to match (search and replace all occurrences)
- Verify: `grep "platform :ios" ios/Podfile` shows 15.0
- What can go wrong: Firebase iOS SDK version may require a higher floor — check Firebase release notes

### Step 6: Update pubspec.yaml SDK Constraint
- Update the `environment.sdk` constraint to match the new Dart SDK:
```yaml
environment:
  sdk: ^X.Y.Z
```
- Bump any dependencies whose constraints conflict with the new SDK (e.g., `intl` was bumped from ^0.19.0 to ^0.20.2 in the 3.41.5 rebase)
- Verify: `fvm flutter pub get` exits 0
- What can go wrong: Dependency version conflicts — resolve by checking pub.dev for compatible versions

### Step 7: Check L10n Generation Path
- Flutter may change where l10n files are generated. In 3.41.5, generation moved from `flutter_gen/gen_l10n/` (synthetic package) to in-place under the arb-dir.
- If changed: update `l10n.yaml` (add/remove `synthetic-package: false`) and update imports in `lib/app.dart` and `lib/core/extensions/context_extension.dart`
- Verify: `fvm flutter pub get` generates localization files and imports resolve

### Step 8: Regenerate Lockfiles and Generated Code
```bash
fvm flutter pub get
dart run build_runner build --delete-conflicting-outputs
cd ios && pod install && cd ..
```
- Verify: All three commands exit 0
- What can go wrong: Pod install may need `pod repo update` first on a stale machine

### Step 9: Apply Release Signing Scaffold
- Check if the fresh build.gradle.kts still has the release signing block reading from `key.properties` / env vars
- If lost in the rebase, re-apply the signing config (see `android/key.properties.template` for the expected format)
- Verify: `grep "key.properties" android/app/build.gradle.kts` finds the signing config

### Step 10: Run Full Verification
```bash
fvm flutter analyze
fvm flutter test
fvm flutter build apk --debug
fvm flutter build ios --debug --no-codesign
```
- All four must exit 0
- What can go wrong: Deprecated APIs in the new SDK — fix lint errors, update API calls

### Step 11: Review the Delta
```bash
git diff --stat
git diff
```
- Walk through every changed file. Key things to check:
  - Android AGP / Kotlin / Gradle versions match the new SDK's defaults
  - iOS deployment target is correct
  - No skeleton-specific customizations were lost (release signing, Podfile floor)
  - `pubspec.lock` dependency versions are reasonable
- Commit when satisfied

### Step 12: Update Documentation
- Update the Version Matrix in README.md
- Update this runbook's "Last performed" date and Flutter version
- Update .planning/rebase_manifest.md if the project uses GSD planning

# Upgrade Playbook

Checklists for common dependency upgrades. Each section is self-contained — jump to the one you need.

Last updated: 2026-04-18

## 1. FlutterFire BoM Bump

When: A new FlutterFire BoM is released and you want to upgrade Firebase packages.

### Steps

1. Check the latest BoM at https://firebase.google.com/docs/flutter/setup
2. Update all Firebase package versions in `pubspec.yaml` as a group (they must stay on the same BoM):
   - firebase_core
   - firebase_auth
   - cloud_firestore
   - firebase_crashlytics
   - firebase_analytics
   - firebase_performance
   - firebase_app_check
3. Run `fvm flutter pub get` — resolve any dependency conflicts
4. Run `fvm flutter analyze` — fix any deprecation warnings introduced by the new versions
5. Run `fvm flutter test` — all tests must pass

### Runtime Verification (REQUIRED — compile-time checks are not sufficient)

6. Build and run on a real device or emulator with Firebase configured:
   ```bash
   fvm flutter run
   ```
7. Verify Firebase initialization completes (check console for "Firebase not configured" warning — should NOT appear if firebase_options.dart is real)
8. Test auth flows: sign in with email, sign in with Google, sign out — verify authStateChanges emits correctly
9. Force a crash in release mode and verify it appears in Firebase Crashlytics Console within 5 minutes
10. Check Firebase Analytics Console for session events

### What Can Go Wrong

- **Breaking API changes:** Firebase packages occasionally rename classes or methods. Check the CHANGELOG for each package.
- **Native SDK version conflicts:** iOS `Podfile.lock` may pin an older Firebase iOS SDK. Run `cd ios && pod update && cd ..` to resolve.
- **App Check provider rename:** If `AndroidProvider` or `AppleProvider` enums change, update `lib/startup_service.dart`.

## 2. App Check Verification

When: After any Firebase upgrade, or when switching App Check providers.

### Steps

1. Verify App Check activation code in `lib/startup_service.dart`:
   - Wrapped in `if (kReleaseMode)` check
   - Android uses `AndroidProvider.playIntegrity`
   - iOS uses `AppleProvider.appAttest`
2. Build a RELEASE build:
   ```bash
   fvm flutter build apk --release
   fvm flutter build ios --release --no-codesign
   ```
3. Install the release APK on a physical Android device
4. Open Firebase Console > App Check > Monitor
5. Verify attestation requests appear from the device

### What Can Go Wrong

- **Provider enum renamed:** If the `AndroidProvider` or `AppleProvider` enums change in a new firebase_app_check version, the code will fail at compile time — update the enum values.
- **Play Integrity not enrolled:** Android App Check requires enrollment in Google Play Console > Release > App integrity. Without this, attestation fails silently.
- **App Attest simulator limitation:** App Attest does not work on iOS Simulator — test on a physical device only.

## 3. auto_route Guard Migration

When: Upgrading auto_route to a new major version.

### Current Setup (auto_route 11)

- `AppRouter` extends `RootStackRouter` directly (no `$AppRouter` codegen base class)
- Guards declared via `guards` getter override on `AppRouter` — currently `[OnboardingGuard]` globally
- `AuthGuard` applied per-route on `LoginRoute` via the `guards` parameter in `AutoRoute()`
- `reevaluateListenable` set on `RouterConfig` in `lib/app.dart` via `Listenable.merge`
- Route generation: `@RoutePage()` annotation + `build_runner`

### Migration Steps

1. Read the auto_route CHANGELOG for the new major version
2. Check if `RootStackRouter` API changed — look for:
   - `guards` getter signature
   - `AutoRoute()` constructor parameters
   - `RoutePage` annotation changes
3. Check if `reevaluateListenable` parameter still exists on `RouterConfig`
4. Update `pubspec.yaml`: both `auto_route` and `auto_route_generator`
5. Run `fvm flutter pub get`
6. Run `dart run build_runner build --delete-conflicting-outputs` — regenerate router.gr.dart
7. Fix any compile errors in:
   - `lib/core/router/router.dart` (guard declarations)
   - `lib/core/router/guards/auth_guard.dart` (guard interface)
   - `lib/core/router/guards/onboarding_guard.dart` (guard interface)
   - `lib/app.dart` (reevaluateListenable wiring)
   - `lib/main.dart` (AppRouter constructor)
8. Run `fvm flutter analyze`
9. Run `fvm flutter test`

### Runtime Verification

10. Launch app — verify onboarding guard redirects on first run
11. Complete onboarding — verify home page loads
12. Navigate to login — verify AuthGuard is applied
13. Check that back navigation works (maybePop)

### Historical Notes

- auto_route 9 -> 11: Removed `$AppRouter` codegen base class, moved guards from class-level implemented interface to `guards` getter, renamed `pushNamed` -> `pushPath` and `pop` -> `maybePop`

## 4. Drift Schema Migration

When: Adding new tables, columns, or modifying the Drift schema.

### Current Setup

- `AppDatabase` in `lib/core/database/app_database.dart`
- Schema version tracked via `@DriftDatabase(tables: [...])` annotation
- Registered as `@lazySingleton` in DI

### Adding a New Table

1. Create the table class (extends `Table`) in `lib/core/database/tables/`
2. Add it to the `@DriftDatabase(tables: [...])` annotation in `app_database.dart`
3. Increment `schemaVersion` in `AppDatabase`
4. Add a migration step in `migration` getter:
   ```dart
   @override
   MigrationStrategy get migration => MigrationStrategy(
     onCreate: (m) => m.createAll(),
     onUpgrade: (m, from, to) async {
       // Add migration steps here
       if (from < 2) {
         await m.createTable(newTableName);
       }
     },
   );
   ```
5. Regenerate: `dart run build_runner build --delete-conflicting-outputs`
6. Run `fvm flutter analyze`
7. Run `fvm flutter test` — repository tests use `NativeDatabase.memory()` which runs onCreate from scratch, so they verify the current schema

### Verifying Migration on Existing Data

8. Install the OLD version of the app on a device
9. Create some data (e.g., increment the counter)
10. Install the NEW version over it (upgrade install, not clean install)
11. Verify existing data is preserved and new tables/columns are available

### What Can Go Wrong

- **Missing migration step:** If you increment schemaVersion but don't add an onUpgrade handler, existing users' databases will fail to open. Always test upgrade installs.
- **Column type change:** Drift does not auto-migrate column types. Manual SQL (`customStatement`) needed for ALTER TABLE operations.
- **Generated code stale:** After schema changes, ALWAYS run build_runner. Stale .g.dart files cause confusing type errors.
