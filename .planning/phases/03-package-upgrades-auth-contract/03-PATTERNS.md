### `lib/core/auth/auth_service.dart` (service abstract, streaming + request-response)

**Analog:** `lib/core/preferences/preferences_service.dart`

**File structure pattern** (lines 1-27):
The project places abstract service interfaces in their own file, with doc comments on the class and each method. No imports beyond core Dart types and project entities.

```dart
/// Abstract preferences service for key-value persistence.
///
/// Features define their own key constants -- this service provides
/// the typed get/set plumbing.
abstract class PreferencesService {
  /// Reads a boolean value for [key], or `null` if not set.
  Future<bool?> getBool(String key);

  /// Writes a boolean [value] for [key].
  Future<void> setBool(String key, {required bool value});
  // ...
}
```

**Key conventions to copy:**
- Doc comment on the abstract class describes purpose
- Doc comment on each method
- Named parameters use `{required ...}` syntax
- No DI annotations on the abstract class (only on impl)
- File contains only the abstract class, no impl

**Secondary analog:** `lib/features/home_page/domain/counter_service.dart` (lines 8-17) -- shows abstract + impl in the same file with `@LazySingleton(as:)`. However, for `core/` services the project separates abstract from impl into different files. Follow the `preferences_service.dart` / `preferences_service_impl.dart` split pattern.

import 'package:skeleton/core/errors/failures.dart';

/// Sealed result type for error handling.
///
/// Use exhaustive `switch` pattern matching to consume:
/// ```dart
/// switch (result) {
///   case Success(:final value): // handle success
///   case Failure(:final failure): // handle failure
/// }
/// ```
sealed class Result<T> {
  const Result();
}

/// Successful result containing [value].
final class Success<T> extends Result<T> {
  const Success(this.value);

  final T value;
}

/// Failed result containing an [AppFailure].
final class Failure<T> extends Result<T> {
  const Failure(this.failure);

  final AppFailure failure;
}
```

**Key conventions to copy:**
- `sealed class` base with `const` constructor
- `final class` for each variant
- `const` constructors on variants
- Doc comment on the sealed class includes a `switch` usage example
- Doc comment on each variant class
- Import only what's needed (`failures.dart` for the failure type)
- No generics needed on `AuthResult` (unlike `Result<T>`) since it always carries `AuthUser`

## Shared Patterns

### Abstract + Impl Service Pattern
**Source:** `lib/core/preferences/preferences_service.dart` + `lib/core/preferences/preferences_service_impl.dart`
**Apply to:** `auth_service.dart` + `fake_auth_service.dart`

Convention:
1. Abstract class in its own file, no annotations
2. Impl in a separate `_impl.dart` file (or named file like `fake_auth_service.dart`)
3. `@LazySingleton(as: AbstractType)` on impl
4. `implements` not `extends`
5. Doc comment on impl references the backing mechanism

### Sealed Class Pattern
**Source:** `lib/core/errors/result.dart` (lines 12-28)
**Apply to:** `auth_result.dart`

Convention:
1. `sealed class` base with `const` constructor
2. `final class` for each variant with `const` constructor
3. Doc comment includes `switch` usage example
4. Each variant documented separately

### Entity with copyWith Pattern
**Source:** `lib/features/home_page/data/model/counter_model.dart` (lines 1-19)
**Apply to:** `auth_user.dart`

Convention:
1. `const` constructor, named `required` parameters
2. All fields `final`
3. `copyWith` with `??` coalescing

### AppFailure Subtype Pattern
**Source:** `lib/core/errors/failures.dart` (lines 12-19)
**Apply to:** Adding `AuthError` to `failures.dart`

Convention:
1. `final class` extending `AppFailure`
2. `const` constructor with `super.message`
3. Single-line doc comment

### @RoutePage Annotation Pattern
**Source:** `lib/features/home_page/presentation/home_page.dart` (lines 1-11)
**Apply to:** `login_page.dart`

Convention:
1. `@RoutePage()` annotation
2. `const` constructor with `{super.key}`
3. Import `auto_route` and `material`

### DI Resolution in main.dart
**Source:** `lib/main.dart` (lines 1-14) + `lib/core/injectable/injection.dart` (line 12)
**Apply to:** Updated `main.dart`

Convention:
1. `getIt<T>()` to resolve singletons after `StartUpService.initServices()` completes
2. Pass resolved instances explicitly to `AppRouter` and `MyApp` constructors
